# ASTRA 提示词工程设计

目标：用户只输入一句话，系统直接生成一份可复制执行、可验收的提示词，而不是要求用户先填写场景、角色、格式等选项。

## 参考依据

本实现查阅并吸收了以下官方资料（访问日期：2026-11）：

1. [OpenAI · Prompt engineering](https://platform.openai.com/docs/guides/prompt-engineering)
   - 采用 Identity → Instructions → Examples → Context 的信息组织方式。
   - 指令和资料使用 Markdown / XML 边界分开；少样本示例用于校准输出。
   - 提示词需要系统化测试与评估，而不是凭感觉修改。
2. [Anthropic · Prompting best practices](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)
   - 清晰直接，说明背景和约束原因；顺序重要时使用明确步骤。
   - 相关、有差异且结构化的 few-shot 示例。
   - 复杂任务可拆成 generate → review → refine 链路，交付前按标准自检。
3. [Anthropic · Define success criteria and build evaluations](https://docs.anthropic.com/en/docs/test-and-evaluate/develop-tests)
   - 先定义具体、可衡量的成功标准。
   - 能自动判定的项目优先用代码评分；结构合格不等于最终回答一定优秀。
4. [Google Gemini · Prompt design strategies](https://ai.google.dev/gemini-api/docs/prompting-strategies)
   - 精确直接、结构一致、明确参数、复杂任务分步。
5. [Anthropic Skills · skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)
   - 提示词保持精简，解释为什么，而不是不断堆叠强制性规则。
   - 用真实测试输入评估并迭代。

## 实际流水线

### 01 · ANALYZE — AI 需求判定

`src/ai/engine.ts` 调用真实模型，输出结构化需求：

- 具体领域与专业角色
- 真实目标、受众、交付物、语气和呈现形式
- 原文事实与硬性约束
- 可观察的成功标准
- 隐含需求与最少默认假设
- 最多两个可选澄清问题（内部分析使用；不阻断用户直接生成）
- 任务复杂度与备选项

原文事实和模型推断分开保存。若模型把领域写得很具体、类别却仍返回 `general`，系统根据领域证据二次校正，避免网页开发等任务落入通用蓝图。

### 02 · BLUEPRINT — 任务结构蓝图

`src/ai/blueprint.ts` 按任务类型选择专业执行步骤和验收项，并组成五段结构：

1. **目标与交付**：做什么、给谁用、为什么这样做。
2. **原始需求与已知信息**：原文逐字放在 `<user_request>` 中，事实与默认假设分开。
3. **执行步骤**：由领域决定的必要步骤，顺序重要时编号。
4. **输出契约**：交付物、结构、格式、语气、篇幅和必须包含的内容。
5. **质量检查**：2–4 条可观察的验收标准，要求执行模型内部核对。

蓝图只提供骨架，所有任务内容由 AI 根据当前需求生成。简单任务会压缩步骤，避免为了“看起来专业”而无限拉长。

### 03 · COMPILE — AI 生成

`src/ai/cases.ts` 按领域选择相关案例作为 few-shot 示范。案例只校准写法和具体程度，不提供本次任务事实。

生成结果必须：

- 保留用户原文与全部明确约束。
- 不要求执行模型先提问或等待资料。
- 使用明确标注的默认假设直接完成。
- 不编造事实、数据、引用、经历或承诺。
- 只包含提示词本身，无开场白、解释或代码围栏。

### 04 · EVALUATE — 校验与返修

`src/ai/quality.ts` 对 AI 结果做 8 项确定性检查：

| 检查 | 验证内容 |
| --- | --- |
| 原始需求保留 | 原文未丢失，意图未被替换 |
| 硬性约束未丢失 | 每条原文约束均被覆盖（支持中英文近似匹配） |
| 指令与资料分层 | 至少三个结构区块，原始输入独立分隔 |
| 输出契约明确 | 有交付形式、结构、格式或篇幅要求 |
| 成功标准可检查 | 包含交付前质量检查 |
| 无需等待即可执行 | 不存在“先回答 / 补充后再 / 等待提供”等阻断表达 |
| 假设与事实边界 | 默认假设有标注，并明确不编造事实 |
| 可直接复制使用 | 长度合理，无额外解释或代码围栏 |

关键项失败时，系统把失败原因交给 AI 自动返修一次。对于“不编造事实”这种可明确判定的安全契约，如果小模型返修后仍遗漏，最后由代码补齐，并在改动记录中说明。最终界面显示真实检查项，不伪造通过。

> 工程校验分数只表示提示词结构与约束是否合格，不代表模型回答一定准确。实际效果仍应通过同模型「效果试跑」和人工验收判断。工作台已简化为整行输入框与其下方原位结果区；生成进度、最终提示词和错误都在同一位置切换，案例只在输入为空时出现。检查与试跑折叠在结果下方，不要求用户先读分析卡。

## 通道与限制

- **免费 AI（Pollinations / GPT-OSS 20B）**：每 45 秒一次回复，界面显示真实排队倒计时。推理强度设为 low，并给推理与 JSON 输出预留 token；案例上下文会压缩，避免小模型只输出分析、不输出提示词。
- **自定义 OpenAI 兼容接口**：需求判定与构建分步调用，可探测模型；Key 仅保留在当前标签页会话中。
- **离线模式**：明确标注不调用 AI，只作为网络或接口失败时的兜底。

## 实测覆盖

使用真实免费 AI 验证过：

- 「帮我写封给客户的道歉邮件，项目延期两周，语气诚恳，不要太长」
- 「帮我构建一个优美的网页」
- 「给我的小店想个名字」

覆盖了领域识别、五段结构、原文保留、约束覆盖、默认假设、直接执行、JSON 异常恢复、token 截断处理、自动返修和最终质量检查。

## 前端构建参考与编译规则

以下三处资料提供不同层次的启发，**不是**用户的产品事实，也不表示可以复制其网站或付费模板提示词：

1. [Recent · Websites](https://recent.design/websites) 是按 SaaS、作品集、电商、编辑内容等用途浏览的网站灵感画廊，不是现成提示词库。[About Recent](https://recent.design/info) 说明其为精选设计收集。编译时先确定网站类型和访客要完成的事情，再选视觉方向，而不是先选一个时髦颜色。
2. [Refero Styles · DESIGN.md template](https://styles.refero.design/design-md/design-md-template) 和 [Design prompts](https://styles.refero.design/ai-agents/design-prompts) 把网站观察记录成字体职责（展示字 / 正文）、颜色职责（画布 / 表面 / 文字 / 行动色）、内容宽度、重复的间距节奏和开放问题。参考只提供视觉规则，**不能**替用户决定真实文案、功能或产品事实；其 DESIGN.md 也不是品牌官方规范。
3. [Scrolltide · one-prompt tutorial](https://www.scrolltide.co/academy/build-an-animated-website-from-one-prompt) 和 [Why Scrolltide](https://www.scrolltide.co/why-scrolltide) 把版式区域、字体尺度、色彩比例、段落顺序、动效触发、时长、缓动、断点、焦点态、reduced-motion 和素材加载写成构建决策。公开教程强调与产品领域匹配、先预览再小步修改；付费库中的完整提示词未被获取或使用。

`src/ai/frontend.ts` 将这些**公开的通用原则**变成可复用的前端构建技能，按原句判别落地页、作品集、店铺、编辑网站、产品工作台、组件或现有网站改版：

- 原文给出的用途、风格、技术栈、功能和参考链接逐条保留；未提供的品牌、价格、客户、素材保持未知。AI 的视觉方向显示为“设计建议”，不冒称用户事实。
- 落地页首屏聚焦一个品牌主张、一个主要行动与产品/场景主视觉；产品控制台则以数据和操作为视觉锚点，**不**强加满幅营销 hero。摄影作品集让作品成为主角；网店优先保证商品信息和购买路径。
- 每次明确构图、字阶、颜色职责、素材方案和有真实行为的交互；只有适合时才规定 2–3 个有目的的动效，说明触发、时长和 reduced-motion 处理。
- 有仓库时沿用其技术栈；空项目才选最小可运行方案。生成结果要求手机/桌面、键盘、焦点态与主要操作可验证。前端专属检查会加入质量报告，不以“好看”这个无法验收的词代替标准。
- 示例仅在**同类建站请求**中选取。网站请求不会再拿“批量改照片名的脚本”作为 few-shot 示例。英文输入采用英文示例与英文章节名。

对「I want to make a beautiful website」，系统只知道“网站需要美观”。它应选一条**标明为暂定**的、可运行的演示方向，明确留白、字体、颜色、主视觉、交互和验收，不得自动宣称用户经营一家店或强制输出单文件 HTML。对更具体的「给摄影师做安静的作品集」「给陶瓷店做可筛选的网店」，内容结构、视觉锚点和交互要求必须随原句改变。
